# [PR 61](https://github.com/exoma-ch/brother-printer/pull/61) build(devkit): upgrade to 1.18.0 and move to the nix dev shell (#60)

## Description

Upgrades the development environment from vigOS devkit `0.3.4` to `1.18.0` and
switches the delivery mode from `devcontainer` to `direnv`. The repo was
scaffolded on 2026-05-28 and never upgraded, leaving it ~26 releases behind,
across the `1.0.0` Debian-to-Nix re-platform of the shared image.

**The move off the container is forced, not stylistic.** `post-create.sh` had
been hand-edited to `apt-get install libusb-1.0-0`, because pyusb resolves its
backend through `ctypes.util.find_library` at import time. The `1.18.0` image is
Nix-built: no `apt`, no `nix` CLI inside it, and `libusb` is absent from devkit's
toolchain SSoT. Container mode also scaffolds no project flake, so there is
nowhere to declare the library. `direnv` mode is the better fit for a USB driver
anyway — the host owns the device, so no `/dev/bus/usb` passthrough, no
rootless-Podman uid remapping, and no container-specific udev rule to maintain.

### Two things reviewers should know

**The release `just` recipes are vendored, and that is upstream's gap.** devkit
defines `prepare-release`, `finalize-release`, `promote-release`,
`publish-candidate`, `abandon-release`, `changelog-preview`, `reset-changelog`
and the `gh-*` helpers **only** in `.devcontainer/justfile.gh`, which `direnv`
mode does not ship — the repo-root `justfile` carries just `help`, `doctor` and
`with-native-libs`. The release *workflows* are unaffected: all 17 are
scaffolded in every mode and `1.18.0` made them mode-aware. Only the local
dispatchers disappeared, and they are thin `gh workflow run` wrappers, so they
are copied verbatim into the preserved `justfile.project`. They are now
consumer-owned and will not track devkit. Filed upstream as
vig-os/devkit#1823, which also notes the `1.18.0` `/devkit:release-*` plugin
skills depend on these same recipes and are therefore unusable in
`direnv`/`bare` mode.

**`worktree` is opted out.** Its recipes lived in
`.devcontainer/justfile.worktree` (418 lines of real logic, not worth
vendoring), so `DEVKIT_FEATURES_DISABLED=worktree` makes the loss explicit and
prunes the 9 now-dead `worktree_*` agent skills.

### CI findings from the first run

Two checks failed. Both are consequences of leaving the container, and neither
is a defect in the scaffold upgrade itself. `Scaffold Drift` and
`Devkit staleness` passed, so the upgrade is internally consistent.

#### 1. Nine golden-image tests — fixed in c709500

Byte-exact golden comparison cannot survive this move, and the reason is by
design in devkit. `setup-devkit-toolchain` forwards `UV_PYTHON` **only when the
runner is NixOS**:

```bash
UV_PYTHON|UV_PYTHON_DOWNLOADS)
  if [ "$devkit_runner_is_nixos" = true ]; then
    return 1          # forwarded
  fi
  return 0 ;;         # denied
```

So hosted CI built the venv on `/usr/bin/python3` (3.14.4) while the dev shell
uses the Nix store interpreter (3.14.7). Same Pillow 12.2.0, same committed
`DejaVuSans.ttf` — but glyph advances differ:

| fixture | CI | golden / dev shell |
|---|---|---|
| `single_12mm` | 81 | 82 |
| `align_left/right_24mm` | 354 | 356 |
| `rotate_0_24mm` | 105 | 108 |
| `default_cap_36mm` | 95 | 103 |

**Heights matched exactly in every case** — height comes from the tape width and
the band confinement, not from advances. That observation is what the new
comparator is built on.

No self-hosted NixOS runner exists on `exoma-ch`, so making CI match the dev
shell is not available, and overriding devkit's `UV_PYTHON` decision would
fight the manylinux constraint behind it.

The goldens now assert exact height, width within `max(3px, 10%)`, ink band
count, and scale-normalized ink geometry (coverage, centroid, bbox) within
0.12. Thresholds are calibrated against the committed fixtures: the harshest
plausible drift scores 0.085, an alignment inversion scores 0.50, and
rotation/line-count changes alter the band count outright. A coarse block-mean
metric was tried first and rejected — at a 3px shift it scored *worse* than a
genuine alignment change.

`test_render_compare.py` pins both directions (41 tests) so the tolerance
cannot rot into vacuity. **This does weaken one guarantee:** a sub-pixel hinting
regression under 3px that preserves ink geometry would no longer be caught.
That trade buys a suite that passes in both environments; the alternative was
to stop verifying rendering in CI at all.

#### 2. Dependency Review — still red, needs a decision above this repo

```
Dependency review is not supported on this repository.
Please ensure that Dependency graph is enabled.
```

This is **not** a repo-level toggle. `exoma-ch` has it off org-wide:

```json
{ "plan": "free",
  "dependency_graph_enabled_for_new_repositories": false,
  "dependabot_alerts_enabled_for_new_repositories": false,
  "dependabot_security_updates_enabled_for_new_repositories": false }
```

`PATCH /repos/exoma-ch/brother-printer` with
`security_and_analysis[dependency_graph][status]=enabled` is silently a no-op —
the field is not even reported back — and
`/dependency-graph/sbom` returns 404, confirming the graph is not live.

That posture looks deliberate: devkit's own Renovate preset records that
Dependabot security updates are off org-wide because **Renovate is the
vulnerability-fix channel** (org-config#307). So the managed `ci.yml` is
hard-requiring a GitHub feature that an org which chose Renovate may
deliberately not have, with no opt-out — `dependency-review` is not covered by
any `DEVKIT_FEATURES_DISABLED` group.

Three ways forward, none of which I'd take unilaterally since the first two
change org-wide security posture:

1. Enable the dependency graph org-wide in `org-config`
2. Enable it for this repo only, if that is possible on Free for public repos
3. Raise it on devkit: `dependency-review` needs an opt-out, a clean skip when
   the graph is unavailable, or `continue-on-error`

Until one is chosen, `CI Summary` stays red on this check alone.

### Correction: Dependency Review — resolved, and my earlier diagnosis was wrong

My comment above claimed the dependency graph "is **not** a repo-level toggle"
and framed this as needing an org-wide decision. That is wrong. It **is** a

enabled at `Settings -> Code security and analysis`. It has now been enabled for
this repo and the graph is live — `/dependency-graph/sbom` returns 32 packages,
and the review API returns 3 changed dependencies for this PR's range.

Where I went wrong: `PATCH /repos/exoma-ch/brother-printer` with
`security_and_analysis[dependency_graph][status]=enabled` silently does nothing
(the field is not echoed back), and I generalised that one failed REST call into
"the setting lives at org level", then went looking for org-level evidence and
found a plausible-looking story in the `exoma-ch` vs `vig-os` org flags. Those
flags only set the default for *new* repositories; they were never what gated
this one.

A second error compounded it: my `/dependency-graph/compare/dev...feature/60-...`
probe 404'd because the head ref contains unencoded slashes, not because the
feature was unavailable. Passing SHAs returns results. I read that 404 as
confirmation of the wrong conclusion.

The org-wide posture discussion in the comment above is therefore moot. For the
record, the one part of it that does hold: `dependabot_security_updates` is

I also no longer think this warrants a devkit issue. "Enable the dependency

#### What this proves

The risk this PR introduced was whether pyusb can find **and open** its libusb
backend from the host dev shell rather than from the container, where it used to
come from `apt-get install libusb-1.0-0` in a managed `post-create.sh`. Proven
three ways:

- `ctypes.util.find_library("usb-1.0")` resolves to `libusb-1.0.so.0` via the
  `LD_LIBRARY_PATH` the flake's `shellHook` exports
- `usb.core.find(...)` plus `set_configuration()` succeeds and reads the
  product and serial descriptors off the device
- the full driver path works: discovery, open/close, status round-trip, the
  library API, and both CLI entry points

The two unrun tests exercise raster encoding and cutter behaviour, which this
change does not touch and which the 358 non-hardware tests already cover. They
were skipped because printing is irreversible, not because anything blocked
them.

#### Host permission note, not a regression

The device node came up `root:lp 0664` from NixOS's own `70-printers.rules`, so
pyusb enumerated the printer but `open()` failed with
`USBError [Errno 13] Access denied` until the node was made writable. That is
the failure mode `docs/install/linux-usb.md` documents, and it is a host setup
step, not a defect introduced here — the container previously masked it by
bind-mounting the node with its own rule.

For a durable fix on a NixOS host, a `TAG+="uaccess"` udev rule in the system
configuration grants the logged-in user access without a `plugdev` group or a
`chmod` that is lost on replug. Both are documented in this PR's revised
dev-shell section. Separately, `packaging/scripts/setup-usb.sh` cannot help on
NixOS at all (distribution package managers, and a read-only
`/etc/udev/rules.d`); that gap also affects NixOS end users of the published
driver and is worth its own issue.
