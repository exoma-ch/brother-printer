# [PR 40](https://github.com/exoma-ch/brother-printer/pull/40) fix: status no longer crashes on no-tape and unknown media/colour bytes (#39)

## Summary

`brother-ptouch-driver status` raised an unhandled `ValueError` whenever the printer reported a media-type or tape-colour byte not defined in our enums — crashing on the two cases users hit in the field:

- **No tape loaded** → tape-colour byte `0x00` (`TapeColor` had no `0x00`).
- **Self-laminating tape (24/36 mm)** → media-type byte `0x16` (`MediaType` had no `0x16`).

Querying status is exactly how a user expects to learn that no/unknown media is loaded, yet that was the one situation that blew up. This mirrors the graceful degradation `TapeWidth.from_byte` already did, and extends it to every enum field on the status reply.

Fixes #39.

## Changes

**Protocol** (`aa12701`)
- Add `TapeColor.NO_TAPE` (`0x00`) and the documented extended-palette colours (reference table 8); add `MediaType.SELF_LAMINATING` (`0x16`) — reported by hardware in the field though absent from Brother's published P900 table.
- `_enum_from_byte` now returns the raw `int` for an undocumented byte instead of re-raising; `PrinterStatus` enum fields widen to `Enum | int`. The raw byte stays available for diagnostics.
- Re-export `TapeColor` on the package API surface for the CLI render layer (respects the ADR-0002 import boundary).

**CLI** (`4226fd4`)
- New `_format_enum` helper: friendly name for a known enum member, else `unknown (0xNN)`. Used for the Color and Media lines; `_format_phase` hardened against the int fallback.
- `TapeColor.NO_TAPE` renders as `No tape`.
